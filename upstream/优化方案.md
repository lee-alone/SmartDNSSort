# 上游查询超时优化方案

## 🎯 优化目标

针对**单服务器场景**(如仅使用本地unbound递归),当前500ms的自适应超时过于激进,导致大量查询被误判超时。

## 📊 当前问题

### 现状:
- 单服务器时自动选择 `sequential` 策略
- 自适应超时 = 平均延迟 × 1.5,范围 500ms~2s
- 初始平均延迟 = 200ms → 首次查询仅给 500ms
- **问题**: 本地递归首次查询通常需要1-3秒,500ms严重不足

### 根本原因:
1. ❌ 没有区分单/多服务器场景
2. ❌ 样本不足时就启动自适应(< 10次查询就开始调整)
3. ❌ 500ms下限对递归查询过于激进

## ✨ 优化方案

### 1️⃣ 添加查询计数器
```go
type Manager struct {
    // ... 现有字段 ...
    totalQueryCount int64  // 总查询次数(原子操作)
}
```

### 2️⃣ 单服务器特殊超时策略
```go
func (u *Manager) GetAdaptiveSequentialTimeout() time.Duration {
    serverCount := len(u.servers)
    
    // === 单服务器场景: 宽松超时策略 ===
    if serverCount == 1 {
        // 样本不足时: 使用保守默认值 2000ms
        if u.totalQueryCount < 50 {
            return 2000 * time.Millisecond
        }
        
        // 样本充足后: 基于实际延迟自适应
        avgLatency := u.GetAverageLatency()
        timeout := time.Duration(float64(avgLatency) * 2.0)  // 更宽松的倍数
        
        // 范围: 1000ms ~ 5000ms (比多服务器更宽松)
        return max(1000*time.Millisecond, min(timeout, 5*time.Second))
    }
    
    // === 多服务器场景: 激进超时策略 ===
    if u.totalQueryCount < 20 {
        return 500 * time.Millisecond  // 多服务器默认值
    }
    
    avgLatency := u.GetAverageLatency()
    timeout := time.Duration(float64(avgLatency) * 1.5)
    return max(500*time.Millisecond, min(timeout, 2*time.Second))
}
```

### 3️⃣ 查询计数器更新

## 📈 优化效果

### 场景1: 单服务器(本地unbound)
| 查询次数 | 超时设置 | 说明 |
|---------|---------|------|
| 1-50次  | 2000ms  | 保守默认值,覆盖大部分递归查询 |
| 50次后  | 1000-5000ms | 基于实际延迟自适应 |

**示例**:
- 首次查询: 2000ms (足够完成递归查询)
- 50次后平均延迟100ms: 100 × 2.0 = 200ms → 限制到 **1000ms**
- 网络波动导致平均延迟500ms: 500 × 2.0 = **1000ms**
- 平均延迟3秒: 3000 × 2.0 = 6000ms → 限制到 **5000ms**

### 场景2: 多服务器(3个以上公共DNS)
| 查询次数 | 超时设置 | 说明 |
|---------|---------|------|
| 1-20次  | 500ms   | 激进默认值,快速失败切换 |
| 20次后  | 500-2000ms | 基于实际延迟自适应 |

## 🔍 设计理由

### Q1: 为什么单服务器要50次才开始自适应?
**A**: 
- 前几次查询可能包含冷启动、网络波动等异常
- 50次查询能代表真实网络状况
- 避免过早自适应导致参数偏移

### Q2: 为什么单服务器下限是1000ms而不是500ms?
**A**:
- 本地递归查询通常涉及多次上游请求
- 500ms对于递归链路过于激进
- 1000ms是经验值,覆盖90%的正常递归查询

### Q3: 为什么单服务器倍数是2.0而不是1.5?
**A**:
- 单服务器没有备用,必须给更多容忍度
- 2.0倍能应对网络波动而不轻易超时
- 上限5秒防止无限等待

### Q4: 为什么多服务器保持500ms?
**A**:
- 多服务器可以快速失败并切换到下一个
- 激进超时能更快发现慢服务器
- 总体查询时间 = 500ms × 服务器数量,仍然合理
